# LIVE 기능 명세서

> live-service의 상세 기능 명세입니다.
서비스 간 흐름·책임 경계는 루트 `docs/PRD.md`, 공통 규칙(에러코드/보안 등)은 `.claude/rules/`를 참고하세요.
기능 블록은 요구사항정의서 **절 번호 + 화면코드**로 식별합니다.
>
>
> **`우선순위`(MVP/P1/P2)는 요구사항정의서에 없는 BE 착수 판단입니다.**
> 구현 순서와 마이그레이션 분할에 쓰고 있습니다.
> 정책상 조정이 필요하면 알려주세요.
>

## 범위

이 문서는 live-service가 담당하는 **LIVE 생성·설정·송출·채팅·AI 큐시트·LIVE 검증·하이라이트·라이브 쿠폰 발행**을 다룹니다.

경계 밖 항목은 아래와 같습니다. 이 서비스에 구현하지 않습니다.

| 항목 | 담당 | 근거 |
| --- | --- | --- |
| LIVE 시작 알림 **발송**, 알림 신청자 목록 | notification-service | 신청 테이블(`live_notify_requests`)을 그쪽이 소유. live는 `notification.raised.v1` 발행만 |
| 판매자 팔로우 | member-service | `follows` 테이블 (#58) |
| **쿠폰 전체**(발급·클레임·사용·복원·정산 차감, 라이브 쿠폰 포함) | order-service | `coupons.issue_channel='LIVE'`로 이미 지원. live는 "진행 중인가"만 답한다(담당자 협의 확정) |
| 프로젝트·리워드 정보 | project-service | live는 `projectId`로 참조만 |
| AI 분석 자체(큐시트 생성·질문 클러스터링·구간 판별) | AI 파트 | live가 컨텍스트를 조립해 `/api/v1/ai`로 호출하고 결과를 저장·노출한다. **AI는 live DB에 접근하지 않는다**(협의 확정). FE는 AI 서버를 직접 부르지 않는다 |

## 기능 목록

### LIVE 생성·설정

#### LIVE 생성

| 항목 | 내용 |
| --- | --- |
| 요구사항정의서 | 6.1.4 |
| 화면코드 | FL_S_LV_01_01 |
| 권한 | 로그인(본인 소유 프로젝트) |
| 우선순위 | **MVP** |
| 트리거 | API 호출 |
- **요구사항**: 판매자가 현재 프로젝트와 연결된 LIVE 방송을 생성한다.
- **처리 내용**: 프로젝트 소유 검증 후 `live_sessions` 레코드를 `DRAFT` 상태로 생성하고 프로젝트·리워드 정보를 연결한다. 판매자 채널(`live_channels`)이 없으면 IVS 채널을 함께 프로비저닝한다.
- **입력값**: `projectId`(project-service `public_id`, UUID)
- **출력값**: `liveId`(`live_sessions.public_id`, UUID), 상태
- **예외 처리**: 타인 소유 프로젝트 → 403 / 없는 프로젝트 → 404 / 생성 실패 → 재시도 안내
- **보안/권한** (S4·S7): 본인 소유 프로젝트에만 생성 가능(S4) · IVS 프로비저닝 응답값 검증(S7)

> 생성 직후 상태를 `SCHEDULED`가 아니라 **`DRAFT`** 로 두는 이유
방송 예정일시는 다음 단계(요구사항정의서 6.2.4.1)에서 받으므로, 이 시점에 예약 상태로 두면 예정 시각 없는 예약이 된다.
>

#### AI 큐시트 생성/조회/수정

| 항목 | 내용 |
| --- | --- |
| 요구사항정의서 | 6.2.4.2 |
| 화면코드 | FL_S_LV_01_02 |
| 권한 | 로그인(본인 소유 LIVE) |
| 우선순위 | P1 |
| 트리거 | API 호출(비동기) |
- **요구사항**: 프로젝트 상세 정보·펀딩 스토리를 기반으로 AI가 방송 진행 순서·대사 초안을 생성하고, 판매자가 편집한다.
- **처리 내용**: 비동기 생성 요청 후 `live_cue_sheets`에 `GENERATING` 상태로 적재. 완료 시 구간 배열(순서·제목·주요 내용·예상 시간·대사)을 저장한다. 판매자는 텍스트 수정·구간 추가·순서 변경이 가능하다.
- **입력값**: `mode`(SCENARIO/SCRIPT), 목표 방송시간, 시연 가능 여부, 강조 포인트, 진행 톤, 필수 언급 문구
- **출력값**: 구간별 순서·주요 내용·예상 시간·대사 초안
- **예외 처리**: 목표 시간 600초 초과 → 400 / 이미 `GENERATING` → 409(중복 요청 방지) / 생성 실패 → `FAILED` + 재시도 안내
- **보안/권한** (S4·S7): AI 연동 응답값 구조·길이 검증 후 저장(S7) · 본인 소유 LIVE만 처리(S4)

> `jobId`를 발급하지 않는다.
세션당 큐시트가 1개라 `GET /cue-sheet`의 `status` 폴링으로 충분하다.

#### LIVE 시작

| 항목 | 내용 |
| --- | --- |
| 요구사항정의서 | 6.3.4 |
| 화면코드 | FL_S_LV_01_03 |
| 권한 | 로그인(본인 소유 LIVE) |
| 우선순위 | **MVP** |
| 트리거 | API 호출 |
- **요구사항**: 설정된 LIVE 방송을 시작한다.
- **처리 내용**: IVS 송출 시작 처리 후 상태를 `LIVE`로 전이하고 `actual_start_at`을 기록한다. **알림 신청자에게 LIVE 시작 알림이 나가도록 `notification.raised.v1`을 발행**한다.
- **입력값**: `liveId`
- **출력값**: 송출 상태, ingest endpoint
- **예외 처리**: `DRAFT`·`SCHEDULED` 외 상태 → 409 / 송출 오류 → 상태 `ERROR` + `error_detail` 저장 후 안내
- **보안/권한** (S4·S7·S9): 본인 소유 LIVE만 시작(S4) · IVS 응답값 검증(S7) · **스트림 키를 응답에 담지 않음**(S9)

### 실시간 채팅·AI 코파일럿

#### 채팅 접속 토큰 발급

| 항목 | 내용 |
| --- | --- |
| 요구사항정의서 | 6.4.4.1 / 11.3.4 |
| 화면코드 | FL_S_LV_01_04 / FL_B_LV_01_03 |
| 권한 | 로그인(판매자·소비자 공통) |
| 우선순위 | **MVP** |
| 트리거 | API 호출 |
- **요구사항**: 판매자와 시청자가 IVS Chat에 접속할 수 있는 토큰을 발급받는다.
- **처리 내용**: 서버가 `CreateChatToken`을 호출한다. **capabilities는 호출자를 보고 서버가 정한다** — 방송 소유자는 `SEND_MESSAGE`·`DELETE_MESSAGE`·`DISCONNECT_USER`, 그 외 로그인 사용자는 `SEND_MESSAGE`. 표시명·프로필은 토큰 `attributes`에 서버가 실어준다.
- **입력값**: `liveId`
- **출력값**: 채팅 토큰, 만료 시각, 룸 ARN, 부여된 capabilities
- **예외 처리**: 진행 중(`LIVE`) 아닌 방송 → 409 / IVS 호출 실패 → 503
- **보안/권한** (S4·S7): **클라이언트는 토큰을 직접 만들 수 없으므로 발급 지점이 곧 인가 지점**(S4) · capabilities·표시명을 요청 본문으로 받지 않음(타인 사칭 차단) · IVS 응답값 검증(S7)

> 초안의 `WS /ws/v1/lives/{liveId}/chat/console`(판매자 LIVE 송출 화면 구독)을 대체한다.
실시간 채팅 표시는 이 토큰으로 IVS Chat에 직접 구독해 해결된다
우리 서버가 중계하지 않는다.
>

#### 채팅 메시지 필터링·적재

| 항목 | 내용 |

- **처리 내용**: 두 경로가 **분리돼 있다.**
    - **필터링** — IVS Chat 리뷰 핸들러(Lambda)가 모든 `SendMessage`에 대해 `ALLOW`/`DENY`/내용 수정을 반환한다. `FallbackResult`는 **`DENY`** 로 설정한다.
    - **적재** — Chat Logging → Kinesis Data Firehose(전파 지연 약 10초) → `POST /internal/v1/lives/chat/messages`. `roomArn`으로 세션을 찾아 `chat_messages`에 넣는다.
- **입력값**: (필터링) 메시지 내용·발신자 / (적재) Firehose 레코드 배치
- **출력값**: (필터링) ALLOW·DENY / (적재) 저장 결과
- **예외 처리**: 차단 시 발신자에게 WebSocket 406 + 사유 / 모르는 룸 레코드는 건너뜀 / 한 레코드 실패가 배치 전체를 실패시키지 않음
- **보안/권한** (S1·S2·S4): 부적절 메시지 서버 필터링(S2) · `messageId` 기준 멱등 적재(재전송 중복 차단) · **적재 엔드포인트를 게이트웨이에 노출하지 않음**(임의 채팅 주입 차단, S4) · 적재 쿼리 바인딩 처리(S1)

> **리뷰 핸들러에서 live-service DB를 호출하지 않는다.**
리뷰 핸들러는 채팅 전송의 동기 경로라, 거기에 우리 DB를 끼우면 우리가 느려질 때 시청자 채팅이 느려지고 우리가 죽으면 채팅이 막히거나 필터링 없이 통과한다.
그래서 적재를 로깅 경로로 분리했다.
>
>
> S3(5분) 대신 Firehose(10초)를 쓰는 이유
> AI 대표질문 집계가 3분 주기라 5분 지연으로는 맞출 수 없다.

#### 라이브 쿠폰 — order-service 위임

| 항목 | 내용 |
| --- | --- |
| 요구사항정의서 | 16.6.4 |
| 화면코드 | FL_B_LV_CP |
| 권한 | (order 소관) |
| 우선순위 | P2 |
| 트리거 | order API 호출 |
- **요구사항**: 방송 중 한정 쿠폰을 메이커가 발행·드롭하고 시청자가 발급받는다.
- **처리 내용**: **live-service는 쿠폰을 만들지도 발급하지도 않는다.** order-service `coupons`가 생애주기 전체를 갖고 있고 LIVE 채널 컬럼(`issue_channel`·`live_session_id`·`drop_type`·`version`)도 이미 들어가 있다.
    - 생성·드롭 → `POST /api/v1/sellers/coupons` (`issueChannel: "LIVE"`)
    - 소비자 클레임 → `POST /api/v1/coupons/{couponCode}/claim`
    - 재고 차감·1인 1매·유효기간 판정 → 전부 order (낙관적 락)
- **live가 제공하는 것**: `GET /internal/v1/lives/{liveId}/status` 하나. order가 "방송 진행 중"을 확인한다.
- **예외 처리**: (order 소관) 재고 소진·유효기간 경과 안내
- **보안/권한** (S4): 진행 중이 아닌 방송의 쿠폰 발급 차단은 위 내부 API 판정에 의존한다

> **소비자 클레임을 live가 감싸지 않는다.**
클라이언트가 order를 직접 부른다
live가 한 번 더 감싸면 재고 차감 경로가 두 개가 되고, 그 순간 낙관적 락이 지켜주던 정합성이 깨진다.
>
>
> ⚠️ **order 담당자 확인 필요**:
> `MakerCouponIssueService`가 `IssueChannel.GENERAL`을 하드코딩하고 있어 현재 그 API로는 LIVE 채널 쿠폰을 만들 수 없다.
> `issueChannel`·`liveSessionId`·`dropType`을 요청으로 받도록 확장이 필요하다.
