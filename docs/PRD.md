# fundit 프로젝트 개요 (PRD)

> 프로젝트의 비즈니스 목적과 서비스 간 흐름만 다룹니다. 화면 단위·API 단위의 상세 스펙은 각 `services/{service}/docs/`를 참고하세요.
>

## 1. 이 프로젝트는 무엇인가 — 문제 → 솔루션 → 기능 매핑

리워드형 크라우드펀딩 + 라이브커머스 플랫폼입니다. 핵심 문제 하나를 여러 기능이 나눠서 풀고 있는 구조입니다.

**핵심 문제** (PRD v0.5, 3.4.1)

> 펀딩 상품은 일반 이커머스보다 사전 정보·사용경험이 부족해 정보 비대칭이 크다
>
> - 구매자: 상세정보만으론 실제 성능·품질 판단 불가 → 펀딩 참여 주저·이탈
> - 판매자: 제품 가치·특성을 효과적으로 전달하기 어려움 → 상세페이지 제작이 진입장벽

| 해결 방향 | 담당 서비스 | 구현된 기능 |
| --- | --- | --- |
| 실시간 검증(LIVE)으로 정보 비대칭·불신 해소 | `live-service` | LIVE 방송, AI 큐시트(방송 전 준비), AI 라이브 코파일럿(방송 중 Q&A 지원) |
| LIVE에서 검증된 정보를 휘발시키지 않고 축적 | `project-service` | LIVE검증 탭 (미시청자도 신뢰 정보 확인) |
| 판매자의 상세페이지 제작 부담 완화 | `project-service` | 펀딩스토리 AI(상세페이지 초안 생성) |
| 펀딩 후 배송 불확실성 해소 (배송지연이 피해유형 1위 51%) | `shipping-service` | 제작·배송 5단계 진행현황 UX |

## 2. 도메인 / 서비스 개요

| # | 도메인 | 서비스 | 핵심 책임                                                                                                      |
| --- | --- | --- |------------------------------------------------------------------------------------------------------------|
| 1 | 인증 | `auth-service` | 로그인, 본인인증, 토큰 발급/검증/회전, 계정(자격증명) 소유                                                                        |
| 2 | 회원 | `member-service` | 회원 프로필, 구매자/판매자 모드, 약관동의, 찜, 팔로우, 배송지                                                                      |
| 3 | 프로젝트/리워드 | `project-service` | 프로젝트, 리워드/옵션/고시정보, 커뮤니티, 새소식, 후기, 프로젝트 심사                                                                  |
| 4 | 주문 | `order-service` | 펀딩 참여, 주문서, 재고 차감, 목표 달성/미달 판정, 쿠폰 적용                                                                      |
| 5 | 결제 | `payment-service` | 결제 승인/취소, 환불, 정산, 쿠폰 정산 연동. payment/refund/settlement 로직은 현재 단일 서비스로 구현하며, 트래픽·운영 부담이 커지는 시점에 분리 여부를 재검토한다 |
| 6 | 라이브 | `live-service` | 방송 송출, 실시간 채팅(IVS Chat 우선 적용), AI 큐시트/코파일럿, 하이라이트, 라이브 전용 쿠폰                                               |
| 7 | 알림 | `notification-service` | 온사이트/웹푸시/이메일/SMS 발송, 수신설정                                                                                  |
| 8 | 배송 | `shipping-service` | 제작·배송 5단계 진행현황, 발송정보                                                                                       |
| 9 | 검색 | `search-service` | 홈피드, 카테고리 탐색, 키워드 검색                                                                                       |
| — | 게이트웨이 | `platform:gateway-service` | 라우팅 (백엔드 팀 직접 구축)                                                                                          |

각 서비스는 별도 데이터베이스를 갖습니다(물리적 DB 분리, MSA 독립성 원칙). 서비스 간 데이터는 API 호출 또는 이벤트로만 주고받으며, 직접 DB 참조는 하지 않습니다(CLAUDE.md 규칙).

## 3. 핵심 비즈니스 흐름

### 3.1 회원가입·로그인

```
[프론트] 회원가입 요청
   → auth-service: 계정(자격증명) 생성 (아이디/비번 또는 소셜)
   → auth-service가 member-service를 동기 호출: 프로필 생성
   → 실패 시 auth-service가 보상 트랜잭션으로 계정 삭제
   → 성공 시 Access Token(바디) + Refresh Token(httpOnly 쿠키) 발급
```

회원가입 시 부여되는 역할은 `member` / `admin` 두 가지로 나뉘며, 구매자·판매자로 역할이 분리되지 않습니다. 가입 완료된 `member`는 단일 권한으로 구매자 화면과 판매자 화면(모드 전환)에 모두 접근할 수 있고, `admin`은 프로젝트 심사(3.2) 등 운영 기능을 수행합니다.
(근거: 요구사항정의서 v0.3 §1.1.1, §2.1.4)

### 3.2 프로젝트 등록 → 심사 → 공개

```
[판매자] 프로젝트 생성 → 기본정보/상세페이지 작성 → 심사 제출
   → project-service: 상태를 '심사중'으로 전환
   → [운영/관리자] 심사 처리(승인/반려)
   → 승인 시 '진행중(공개)'로 전환, 반려 시 '준비중'으로 되돌림 + 사유 안내
```

### 3.3 펀딩 참여 → 결제 → 목표 판정 → 정산/환불

```
[구매자] 리워드 선택 → 주문서 작성(쿠폰 적용 가능) → 결제 요청
   → order-service: 재고 검증(project-service에 위임) → Order(PENDING) 생성
   → payment-service: PG 연동 결제 처리 → 성공 시 Order.PAID
   ...(펀딩 마감 시점)...
   → order-service: 목표 달성/미달 판정(배치)
   → 달성: payment-service 정산(선정산/최종정산) 진행
   → 미달: payment-service가 전체 참여자 자동 환불 + 쿠폰 복원
```

성립 후에는 단순변심 환불 불가, 하자/발송지연 등 판매자 귀책 사유에 한해 환불 가능(payment-service refund 로직).

### 3.4 LIVE 방송 → 채팅 → 하이라이트 → 펀딩 전환

```
[판매자] LIVE 생성/설정(AI 큐시트) → 방송 시작
   → 시청자 실시간 채팅(IVS Chat), AI가 질문 분류·추천답변 지원
   → 방송 종료 → AI가 채팅 요약 → LIVE검증 탭에 반영(project-service)
   → 다시보기 기반 하이라이트 자동 생성 → 판매자 검토·공개
   → 하이라이트가 프로젝트 상세/홈에 노출되어 펀딩 유입
```

### 3.5 제작 → 배송 → 수령확인

```
펀딩 성립 → shipping-service: 제작 착수 단계 생성
   → 판매자가 주기(1주)마다 진행상황 업데이트(미등록 시 알림)
   → 발송정보(운송장) 등록 → 배송 완료 → 구매자 수령확인(또는 자동 확정 배치)
```

### 3.6 쿠폰 발급 → 적용 → 정산 차감

```
플랫폼(자동) 또는 메이커(수동)가 쿠폰 발급
   → 구매자가 주문서 작성 시 쿠폰 적용(order-service)
   → 결제 완료 시 쿠폰 사용 완료 처리, 환불 유형별 복원 규칙 적용(payment-service)
   → 메이커 발급 쿠폰의 할인분은 정산 시점에 해당 메이커 정산액에서 차감
```
